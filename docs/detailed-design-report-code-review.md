## 오류 1. Gemini 모델명 불일치

### 보고서 내용

보고서 서론 및 제한조건 부분에서 AI 모델을 `Gemini 1.5 Pro`로 설명한다.

예시 표현:

- “AI(Gemini 1.5 Pro)를 활용하여 목표 달성을 위한 세부 작업을 지능적으로 분할한다.”
- “Google Gemini 1.5 Pro API는 외부 네트워크를 통해 호출되므로...”

### 실제 코드

현재 백엔드 설정의 기본 모델은 다음과 같다.

```python
llm_model: str = "gemini-2.5-flash-lite"
```

관련 파일:

- `backend/core/config.py`
- `backend/services/planning.py`

즉, 현재 코드 기준으로는 `Gemini 1.5 Pro`가 아니라 `gemini-2.5-flash-lite`를 기본 모델로 사용한다.
또한 모델명은 환경변수 `LLM_MODEL`을 통해 변경 가능한 구조다.

### 왜 문제인가

보고서가 특정 모델명까지 명시하면, 심사자나 팀원이 실제 코드와 대조했을 때 “구현 모델이 다르다”는 지적을 받을 수 있다.
특히 AI API는 모델명에 따라 성능, 비용, 응답 속도, 기능이 달라지므로 단순한 용어 차이가 아니라 설계 사양 불일치로 보일 수 있다.

### 수정 권장 문장

기존:

> AI(Gemini 1.5 Pro)를 활용하여 목표 달성을 위한 세부 작업을 지능적으로 분할한다.

수정:

> Google Gemini API를 활용하여 사용자의 목표를 분석하고, 목표 달성을 위한 실행 항목을 생성한다. 현재 구현에서는 `gemini-2.5-flash-lite` 모델을 기본값으로 사용하며, 환경변수를 통해 모델을 변경할 수 있도록 설계하였다.

## 오류 2. AI가 목표를 `FlexibleTask`로 분해한다는 설명 오류

### 보고서 내용

보고서에서는 사용자의 큰 목표를 AI가 `FlexibleTask`로 분해한다고 설명한다.

예시 표현:

- “사용자가 입력하는 광범위한 목표를 AI가 논리적인 세부 작업(FlexibleTask)으로 분해”
- “AI 알고리즘에 의해 분할되는 세부 작업(FlexibleTasks)을 효율적으로 저장”

### 실제 코드

현재 코드에서 목표 기반 AI 플래닝의 흐름은 다음과 같다.

1. 사용자가 `/goals/intake`로 목표 문장을 입력한다.
2. 백엔드가 목표 초안과 질문 목록을 생성한다.
3. 사용자가 `/goals/complete`를 호출한다.
4. 백엔드는 `Goal`을 저장한다.
5. 백엔드는 `AIPlan`을 생성한다.
6. 백엔드는 `AIPlanItem` 목록을 생성한다.

즉, AI 목표 분해 결과는 주로 `AIPlanItem`으로 저장된다.

반면 `FlexibleTask`는 사용자가 직접 등록하는 유동 작업에 가깝다.
예를 들어 “과제하기”, “운동하기”, “보고서 작성하기”처럼 사용자가 직접 입력한 작업을 저장하는 모델이다.

관련 코드:

- `backend/api/routes/goals.py`
- `backend/models/ai_plan.py`
- `backend/models/flexible_task.py`
- `backend/services/planning.py`

### 왜 문제인가

이 부분은 단순 표현 문제가 아니라 백엔드 데이터 모델 설명의 핵심 오류다.

현재 백엔드에는 다음 두 종류의 “스케줄 가능한 작업”이 구분되어 있다.

| 구분 | 모델 | 생성 주체 | 설명 |
| --- | --- | --- | --- |
| 유동 작업 | `FlexibleTask` | 사용자 | 사용자가 직접 등록하는 할 일 |
| AI 계획 항목 | `AIPlanItem` | AI/템플릿 플래너 | 목표를 기반으로 생성된 실행 항목 |

보고서가 이 둘을 구분하지 않으면 ERD, API 명세, 스케줄링 알고리즘 설명이 모두 흐려진다.

### 수정 권장 문장

기존:

> 사용자가 입력하는 광범위한 목표를 AI가 논리적인 세부 작업(FlexibleTask)으로 분해한다.

수정:

> 사용자가 입력한 목표는 AI 플래닝 과정을 통해 `AIPlan`과 `AIPlanItem`으로 구조화된다. `AIPlanItem`은 목표 달성을 위한 세부 실행 항목이며, 이후 자동 배정 알고리즘을 통해 사용자의 빈 시간에 배치될 수 있다. 별도로 사용자가 직접 등록하는 유동 작업은 `FlexibleTask`로 관리한다.

## 오류 3. FastAPI 비동기 처리 설명 부정확

### 보고서 내용

보고서에서는 FastAPI 백엔드가 비동기 처리를 통해 AI 연동과 복잡한 스케줄링 연산의 블로킹을 방지한다고 설명한다.

예시 표현:

- “Python 기반의 비동기 처리(Asynchronous I/O)를 통해 AI 연동 및 복잡한 스케줄링 연산 시의 블로킹(Blocking)을 방지”

### 실제 코드

현재 라우트와 서비스는 대부분 동기 방식이다.

예시:

```python
@router.post("/allocate", response_model=AllocateResponse)
def allocate_schedule(...):
    ...
```

```python
@router.post("/google", response_model=LoginResponse)
def login_with_google(...):
    ...
```

또한 DB 세션도 동기 SQLAlchemy 세션을 사용한다.

```python
engine = create_engine(...)
SessionLocal = sessionmaker(...)
```

Google API 검증에도 `httpx.get(...)` 동기 호출을 사용한다.

### 왜 문제인가

FastAPI 자체는 비동기 처리를 지원하지만, 현재 코드가 비동기 구조로 작성된 것은 아니다.
보고서의 표현은 프레임워크의 가능성을 실제 구현된 특성처럼 설명하고 있다.

캡스톤 프로젝트에서 이 정도는 큰 결함은 아니지만, “구현 완료 사항”으로 적으면 코드와 맞지 않는다.

### 수정 권장 문장

기존:

> 백엔드는 FastAPI의 비동기 처리를 통해 AI 연동 및 스케줄링 연산 시 블로킹을 방지하도록 설계하였다.

수정:

> 백엔드는 FastAPI 기반 REST API 서버로 구현하였다. 현재 구현은 동기 SQLAlchemy 세션과 동기 라우트 중심으로 구성되어 있으며, 향후 AI 호출 지연이나 대규모 요청 처리가 필요할 경우 비동기 처리 또는 백그라운드 작업 큐로 확장할 수 있다.

## 오류 4. REST API 통신 규격이 완전히 확립되었다는 표현 과장

### 보고서 내용

보고서에서는 RESTful API 통신 규격이 확립되었다고 설명한다.

예시 표현:

- “RESTful API 및 JWT 기반의 빠르고 안전한 인증 시스템을 구축”
- “프론트엔드와 백엔드의 API 통신 규격을 확립”

### 실제 코드

백엔드에는 많은 API가 구현되어 있지만, 프론트엔드가 기대하는 일부 API가 아직 없다.

프론트엔드가 호출하는데 백엔드에 없는 API:

| 프론트 기대 API | 현재 백엔드 구현 여부 | 영향 |
| --- | --- | --- |
| `GET /schedules/fixed/{schedule_id}` | 없음 | 고정 일정 상세 조회 시 404 가능 |
| `GET /tasks/flexible/{task_id}` | 없음 | 유동 작업 상세 조회 시 404 가능 |
| `POST /goals` | 없음 | 수동 목표 생성 기능 사용 시 404 가능 |

관련 프론트 파일:

- `lib/api.ts`

관련 백엔드 라우트:

- `backend/api/routes/fixed_schedules.py`
- `backend/api/routes/flexible_tasks.py`
- `backend/api/routes/goals.py`

### 왜 문제인가

이 문제는 보고서만의 문제가 아니라 실제 시연 안정성과도 연결된다.
프론트에서 특정 버튼이나 상세 화면이 해당 API를 호출하면 바로 404가 발생할 수 있다.

따라서 보고서에는 “API 규격을 완전히 확립했다”보다는 “핵심 API를 구현했으며 일부 상세 조회/수동 생성 API는 보완 예정” 정도가 더 정확하다.

### 수정 권장 문장

기존:

> RESTful API 통신 규격을 확립하였다.

수정:

> 사용자 인증, 고정 일정, 유동 작업, 목표 플래닝, 자동 배정, 캘린더 조회를 위한 핵심 REST API를 구현하였다. 다만 프론트엔드 상세 화면과의 완전한 정합성을 위해 일부 상세 조회 API와 수동 목표 생성 API는 추가 보완이 필요하다.

## 오류 5. Supabase 고정 사용처럼 표현됨

### 보고서 내용

보고서에서는 데이터베이스를 Supabase 기반으로 설명한다.

예시 표현:

- “Supabase 데이터베이스 기반의 3-Tier 아키텍처”
- “데이터베이스(Supabase)는 실제 상용 환경과 동일하게 클라우드 통신을 유지”
- “Supabase & PostgreSQL”

### 실제 코드

현재 코드는 특정 DB 공급자에 고정되어 있지 않다.

기본 설정:

```python
database_url: str = "sqlite:///./ai_planner.db"
```

Docker Compose:

```yaml
services:
  postgres:
    image: postgres:16
```

`.env.example`에는 Supabase 연결 문자열 예시가 있다.

즉, 현재 구조는 다음과 같이 보는 것이 정확하다.

- 개발 기본값: SQLite
- 로컬 DB 환경: Docker PostgreSQL
- 클라우드 DB 선택지: Supabase PostgreSQL

### 왜 문제인가

보고서가 Supabase를 필수 구성요소처럼 말하면, 실제 코드의 기본 실행 방식과 어긋난다.
특히 시연 환경에서 로컬 PostgreSQL이나 SQLite를 사용할 경우 보고서 설명과 다르게 보일 수 있다.

### 수정 권장 문장

기존:

> 본 시스템은 Supabase 데이터베이스 기반으로 구성된다.

수정:

> 본 시스템은 SQLAlchemy 기반으로 데이터베이스 계층을 추상화하며, 개발 환경에서는 SQLite 또는 로컬 PostgreSQL을 사용할 수 있고, 클라우드 환경에서는 Supabase PostgreSQL과 연동 가능하도록 설계하였다.

## 오류 6. CORS 설정에 Vercel 도메인이 포함되어 있다는 설명 부정확

### 보고서 내용

보고서에서는 CORS 설정에 Localhost 및 Vercel 도메인을 명시한다고 설명한다.

예시 표현:

- “CORSMiddleware에 명시적인 화이트리스트(Localhost 및 Vercel 도메인)를 설정”

### 실제 코드

현재 기본 허용 origin은 다음과 같다.

```python
allowed_origins: list[str] = Field(
    default_factory=lambda: ["http://localhost:3000", "http://localhost:3001"]
)
```

즉, 코드 기본값에는 Vercel 도메인이 없다.
물론 `.env`에서 `ALLOWED_ORIGINS`를 지정하면 Vercel 도메인을 추가할 수 있다.

### 왜 문제인가

보고서 표현만 보면 이미 Vercel 배포 도메인까지 CORS 설정이 완료된 것처럼 보인다.
하지만 현재 코드 기본값만 보면 로컬 개발 환경 중심이다.

### 수정 권장 문장

기존:

> Localhost 및 Vercel 도메인을 CORS 화이트리스트로 설정한다.

수정:

> 현재 기본 CORS 설정은 로컬 개발 환경(`localhost:3000`, `localhost:3001`)을 대상으로 하며, Vercel 배포 시에는 환경변수 `ALLOWED_ORIGINS`에 배포 도메인을 추가하여 대응할 수 있도록 설계하였다.

## 오류 7. JWT 인증 적용 범위 설명 과장

### 보고서 내용

보고서에서는 JWT 기반 인증 시스템을 통해 사용자 데이터가 안전하게 렌더링된다고 설명한다.

예시 표현:

- “RESTful API 및 JWT 기반의 빠르고 안전한 인증 시스템”
- “사용자가 언제 어디서 접속하든 본인의 할 일 데이터와 AI 분석 결과를 안정적으로 렌더링”

### 실제 코드

다음 주요 API들은 JWT 인증을 사용한다.

- 고정 일정 API
- 유동 작업 API
- 목표 목록/상세/수정 API
- 목표 완료 API
- 자동 배정 API
- 캘린더 API
- `/auth/me`

그러나 다음 API들은 공개 상태다.

- `GET /users`
- `GET /users/{user_id}`
- `POST /goals/intake`
- `GET /health`
- 데모 HTML 페이지들

캡스톤 기준으로는 큰 문제로 보지 않을 수 있지만, 보고서의 “안전한 인증 시스템”이라는 표현은 실제 코드보다 강하다.

### 왜 문제인가

보안 관점 질문이 들어오면 공개 API 범위에 대한 설명이 필요하다.
특히 `/users` 공개는 실제 서비스라면 부적절하다.

### 수정 권장 문장

기존:

> JWT 기반의 빠르고 안전한 인증 시스템을 구축하였다.

수정:

> 주요 사용자 데이터 API에는 JWT 인증을 적용하여 사용자별 일정, 작업, 목표 데이터를 분리하였다. 일부 회원 조회 및 데모용 API는 개발 및 시연 편의를 위해 공개되어 있으며, 실제 배포 단계에서는 인증 범위를 확대할 필요가 있다.

## 오류 8. 프롬프트 캐싱 전략이 구현된 것처럼 보일 수 있음

### 보고서 내용

보고서에서는 Gemini API 호출 지연과 토큰 제한에 대응하기 위해 캐싱 전략 또는 로딩 UI 설계가 필수라고 설명한다.

이 문장 자체는 “제약사항”으로는 맞다.
하지만 문맥에 따라 이미 캐싱 전략이 설계 또는 구현된 것처럼 읽힐 수 있다.

### 실제 코드

현재 구현에는 Gemini 실패 시 템플릿 기반 fallback이 존재한다.

즉, 외부 AI 호출이 실패해도 기본 계획을 생성할 수 있는 구조는 있다.

하지만 LLM 응답 캐싱은 구현되어 있지 않다.

### 왜 문제인가

캐싱이 구현되어 있다고 오해되면 실제 코드 검토 시 불일치로 보일 수 있다.

### 수정 권장 문장

기존:

> 중복 호출을 방지하는 캐싱 전략 또는 로딩 UI 설계가 필수적이다.

수정:

> 현재 구현에서는 Gemini API 호출 실패 시 템플릿 기반 fallback을 통해 기본 계획 생성을 보장한다. 다만 중복 호출 방지를 위한 LLM 응답 캐싱은 향후 개선 사항으로 남아 있다.

## 오류 9. 대시보드 알림 컴포넌트 설명 불명확

### 보고서 내용

보고서에는 모바일 푸시 알림 대신 프론트엔드 대시보드 내 알림 컴포넌트를 설계했다고 되어 있다.

예시 표현:

- “프론트엔드 '대시보드' 내에 알림 컴포넌트를 설계”

### 실제 코드

현재 확인되는 프론트엔드 주요 화면은 다음과 같다.

- 메인 페이지
- 일정 관리 페이지
- 주간 스케줄 페이지
- 설정 페이지
- 인증 컨텍스트/버튼

명확한 “대시보드 알림 컴포넌트” 구현은 확인되지 않는다.

### 왜 문제인가

발표 시 실제 화면에 알림 컴포넌트가 없다면, 보고서와 결과물이 다르다는 지적을 받을 수 있다.

### 수정 권장 문장

기존:

> 프론트엔드 대시보드 내에 알림 컴포넌트를 설계하였다.

수정:

> 초기에는 실시간 푸시 알림 기능을 고려하였으나, 현재 구현에서는 핵심 기능인 일정 관리, 목표 플래닝, 캘린더 표시를 우선 구현하였다. 알림 컴포넌트는 향후 사용자 피드백 및 일정 변경 안내 기능으로 확장할 수 있다.

## 오류 10. 데이터 모델 설명 누락

### 보고서 내용

보고서에서는 데이터 모델을 주로 다음 요소 중심으로 설명한다.

- Users
- Goals
- FixedSchedules
- FlexibleTasks

### 실제 코드

현재 백엔드의 핵심 모델은 더 많다.

| 모델 | 역할 |
| --- | --- |
| `User` | 사용자 |
| `AuthAccount` | Google 소셜 로그인 계정 연결 |
| `FixedSchedule` | 고정 일정 |
| `FlexibleTask` | 사용자가 직접 등록하는 유동 작업 |
| `Goal` | 사용자 목표 |
| `AIPlan` | 목표 기반 AI 계획 |
| `AIPlanItem` | AI 계획의 세부 실행 항목 |
| `AllocatedTask` | 자동 배정된 유동 작업 일정 |

### 왜 문제인가

현재 코드의 핵심 기능은 단순히 `Goal`과 `FlexibleTask`만으로 설명되지 않는다.
특히 AI 플래닝 결과를 설명하려면 `AIPlan`과 `AIPlanItem`이 반드시 들어가야 한다.
자동 배정 결과를 설명하려면 `AllocatedTask`도 들어가야 한다.

### 수정 권장 문장

기존:

> 사용자의 포괄적인 목표와 고정 일정, 세부 작업을 저장하는 정규화된 데이터베이스 스키마를 설계하였다.

수정:

> 데이터베이스는 사용자, 소셜 인증 계정, 고정 일정, 유동 작업, 목표, AI 계획, AI 계획 항목, 자동 배정 결과를 분리하여 관리한다. 이를 통해 사용자가 직접 등록한 작업과 AI가 생성한 계획 항목을 구분하고, 캘린더에서는 두 유형의 배정 결과를 통합적으로 조회할 수 있도록 설계하였다.

## 오류 11. “최적화된 스케줄” 및 “오차 없이 매핑” 표현 과장

### 보고서 내용

보고서에는 자동 스케줄링을 다음과 같이 표현한다.

- “최적화된 스케줄”
- “오차 없이 매핑”
- “어떠한 조건에서도 최적화된 스케줄을 도출”

### 실제 코드

현재 자동 배정 알고리즘은 그리디 방식이다.

대략적인 흐름:

1. 고정 일정, 기존 배정 작업, 배정된 AI 계획 항목을 바쁜 시간으로 계산한다.
2. 하루 작업 가능 시간 범위에서 빈 시간을 만든다.
3. 마감일과 우선순위 기준으로 유동 작업을 배정한다.
4. 남은 빈 시간에 AI 계획 항목을 배정한다.

이 방식은 실용적이고 시연에 적합하지만, 수학적으로 최적해를 보장하지는 않는다.

### 왜 문제인가

“최적화”라는 단어는 보고서에서 자주 쓰이지만, 현재 코드는 엄밀한 최적화 알고리즘이라기보다 휴리스틱/그리디 배정 알고리즘이다.
캡스톤 발표에서는 오히려 “현실적인 우선순위 기반 자동 배정”이라고 설명하는 편이 방어하기 좋다.

### 수정 권장 문장

기존:

> 어떠한 조건에서도 최적화된 스케줄을 도출한다.

수정:

> 사용자의 고정 일정과 작업 마감일, 우선순위를 고려하여 가용 시간에 작업을 자동 배치한다. 현재 구현은 그리디 기반 휴리스틱 알고리즘으로, 빠른 응답성과 시연 안정성을 우선하며, 향후 더 정교한 최적화 알고리즘으로 확장 가능하다.

## 보고서에서 유지해도 되는 내용

다음 내용은 현재 코드와 큰 방향이 맞으므로 유지해도 된다.

1. 3-Tier 아키텍처 설명
   - 프론트엔드, 백엔드, 데이터베이스 분리 구조는 코드와 일치한다.

2. Next.js 16 사용
   - `package.json` 기준 `next` 버전은 `16.2.3`이다.

3. FastAPI 백엔드 사용
   - `requirements.txt`와 실제 백엔드 구조가 일치한다.

4. SQLAlchemy와 Alembic 사용
   - 모델과 마이그레이션 디렉터리가 존재한다.

5. JWT 인증 도입
   - 주요 사용자 데이터 API에 JWT 기반 인증이 적용되어 있다.

6. CORS 필요성
   - 프론트와 백엔드가 다른 포트에서 동작하므로 CORS 설명 자체는 적절하다.

7. 그리디 기반 스케줄링 방향
   - 자동 배정 서비스는 실제로 그리디 방식에 가깝다.

8. 외부 지도 API 제거
   - 현재 코드에 지도 API 연동이 없으므로, 핵심 스케줄링에 집중했다는 설명은 유지 가능하다.

## 보고서 수정용 요약 문단

아래 문단은 보고서의 기술 스택/구현 현황 설명을 코드 기준으로 다시 쓸 때 사용할 수 있다.

> 본 시스템은 Next.js 16 기반 프론트엔드와 FastAPI 기반 백엔드를 분리한 3-Tier 구조로 설계되었다. 백엔드는 SQLAlchemy ORM과 Alembic을 사용하여 사용자, 인증 계정, 고정 일정, 유동 작업, 목표, AI 계획, AI 계획 항목, 자동 배정 결과를 관리한다. 목표 기반 플래닝은 Google Gemini API를 활용하되, 현재 구현에서는 `gemini-2.5-flash-lite`를 기본 모델로 사용하며, API 호출 실패 시 템플릿 기반 fallback을 통해 기본 계획 생성을 보장한다. 자동 배정 기능은 사용자의 고정 일정과 기존 배정 내역을 바탕으로 빈 시간대를 계산하고, 마감일과 우선순위를 고려하는 그리디 기반 알고리즘으로 유동 작업 및 AI 계획 항목을 캘린더에 배치한다.
